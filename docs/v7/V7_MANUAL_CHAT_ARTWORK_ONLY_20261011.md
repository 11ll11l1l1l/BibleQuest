# BibleQuest V7 — manual-chat-only image creation, agent QA only
Effective **2026-10-11 JST**, by direct user instruction. This policy supersedes every earlier V7 image-agent generation schedule, prompt, ownership map or instruction, including contradictory passages in V7_VISUAL_ASSET_PRODUCTION_20261008.md, V7_EIGHT_STREAM_ARTWORK_EXECUTION_20261009.md, V7_PRIORITIZED_MILESTONES_20261010.md and historical queue descriptions. It does **not** weaken the image construction guide, rights/Scripture/privacy checks or Lane D release criteria.

## Absolute generation boundary
- **ONLY a user-invoked, live interactive ChatGPT conversation** may make any new BibleQuest V7 image pixels or change existing image pixels. This includes the first original CLEAN image, ALL edited/regenerated CLEAN variants, localized TYPE image, THUMB cropping/typesetting/compositing, Home hero, Needs, Feelings, teaching/book thematic art and all 300 devotional covers. A manual chat may use its image generation or local image-editing tools during the active user-requested session.
- **ALL autonomous/scheduled agents, including former Visual Agents 1–5, Independent Visual QA and A/B/C/D agents**, are *QA-only with respect to artwork*. No autonomous image generation, image editing, image retouching, image export, programmatic image synthesis, proxy image service, prompt delegation to a producer agent, or automatic retry. Do not create/modify/replace image binaries or source vector files in background runs. No user silence counts as approval to produce images.
- Manual lanes **X = missing Feelings/Needs/Home**, **Y = repair rejected/defective variants**, **Z = source-bound individual devotional covers** remain possible **only when the user directly invokes a ChatGPT conversation**. These lane letters are manual-chat task labels, NOT recurring image producers. A user can invoke any V7 artwork chat directly; check current work/PR ownership and avoid duplicate IDs.
- A scheduled QA agent may inspect source files, art binaries, screenshots, sidecars and CI; run deterministic technical/browser tests; post narrowly scoped QA reports or review comments; and request correction by a *manual chat*. It may not quietly perform that correction itself. QA findings must name exact asset ID, PR/commit SHA, inspected files/variants, evidence and PASS/FAIL/HOLD **by its own QA dimension**. No automated review equals user approval.

## QA-only agent assignments
1. **Visual QA 1 — scene, source meaning and Scripture context:** visual narrative, exact prescribed scene/action, biblical reference/context, the complete devotional source.
2. **Visual QA 2 — rights, provenance, wording and localization:** original source, permission/license/font evidence, titles/references, language consistency and disclosure.
3. **Visual QA 3 — technical assets:** exact raster bytes, SHA-256, dimensions, aspect ratio, resolution, TYPE/THUMB, 10% safe margins, Chromium 320/390/430/800px, served SHA.
4. **Visual QA 4 — uniqueness and art direction:** duplication against accepted/open/rejected art, realism, anatomy, visual story, crop, mobile legibility, no clichés.
5. **Independent Visual QA — consolidation:** reconcile findings for each candidate into a documented PASS/FAIL/HOLD, maintain queue, ask the manual-chat owner for changes. It cannot self-approve, merge, deploy or mark productionReady.
6. **Lane A/B/C/D artwork involvement:** inventory/content, independent contextual and rights review, integration/release certification respectively, **never image pixel generation**. Non-art feature development remains allowed under existing project rules.

## New manual-chat candidate handoff
1. Read `AGENTS.md`, `work/RULEBOOK.md`, the locked `docs/v7/unfinished-artwork-guide/00_COMPLETE_CONSTRUCTION_GUIDEBOOK.md` and matching exact-ID chapter; inspect the full approved content/verse, accepted art, open candidate PRs and known-rejected image hashes before starting. Any scene deviation requires written rationale.
2. Generate **one separate original high-resolution raster image per assigned ID** (no collage/SVG/generic substitution). Make CLEAN text-free; create TYPE and THUMB *only within this explicitly invoked manual chat* if required; use only correctly reviewed canonical wording/references; never invent or embed unreviewed Scripture quotations. Keep scene and locale variants exact; preserve good CLEAN when correcting TYPE alone.
3. For **every newly added or changed** `public/v7/images/**` raster binary, add `data/v7/visual-assets/manual-chat-intake/<sha256>.json` with the actual binary SHA-256, repository-relative media path, assigned asset ID, non-secret opaque interactive chat/asset reference, explicit user invocation, guide scene ID, source content ID, and `qaStatus: "pending"`. A first-party statement is an **attestation**, not cryptographic proof of chat identity. The PR must point to the active user-requested manual chat generation handoff. Never fabricate a chat identifier, provenance, bytes or verification.
4. Submit as **candidate/pending QA** in a non-production PR with a truthful sidecar and real bytes. Agents may independently audit the submitted image, but **cannot generate, edit or replace its pixels**. Reject missing/unverifiable assets, stale Scripture/source revisions, defective anatomy/text/format/crop, near duplicates and unsupported provenance.
5. Pass all applicable independent QA dimensions, actual built-app and source-byte checks, rights/context evidence, and **explicit user visual approval** before production promotion. Lane D alone may certify/deploy release after normal strict gates. Previous automated producer assets are **legacy pending/rejected**, never implicitly promoted; the user may explicitly accept an existing candidate after review.
6. On user rejection, remove rejected heavyweight candidate image and related unused derivative files from working source/PR where safely owned; retain only minimal immutable audit evidence (hash, ID, reason) in the rejection log/denylist to stop recycling. Never erase evidence of what was rejected or replace another branch's work.

## Enforcement / limitations
The V7 Visual Asset Built-Browser QA workflow checks that new/modified image binaries have matching *manual chat intake attestations* and measured SHA-256. This mechanical gate proves file-to-record consistency, **not** that an image was truly generated in a live chat or that it looks correct; independent reviewers and user approval are still required. Even a green CI check cannot authorize scheduled agents to generate images. A PR with only QA notes must never claim approved artwork or new image coverage.
