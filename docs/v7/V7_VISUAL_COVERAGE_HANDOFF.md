# V7 visual coverage handoff — Lane A to five image agents / Lane D

The canonical binary, rights, metadata and visual QA validation lives in `scripts/v7-visual-assets-audit.mjs`. Do not interpret three file paths alone as a verified bundle.

```bash
node scripts/v7-visual-assets-audit.mjs --manifest
node scripts/v7-visual-coverage-report.mjs > /tmp/v7-visual-coverage.json
node --test tests/v7/visual-assets-audit.test.mjs tests/v7/visual-coverage-report.test.mjs
```

The coverage report is derived from the **current Git checkout**, not edited by agents. If the underlying image audit fails, `releaseEligible=false`, errors are reported and CLI exits nonzero. It produces an ordered `agents[]` array and a 30-feeling `tasks[]` queue per agent. Each task records its original queue concept, canonical Library emotion ID, accepted asset IDs, verified typography locales, verified thumbnail, pending QA sidecars, safe fallback, and next action.

An original CLEAN master can be released with **live localized text** while its TYPE/THUMB artwork is awaiting QA. However this counts only toward `productionReadyMasters`, **not** `completeThreeFileBundles`. TYPE is only available for its independently reviewed locale. For other locales, use CLEAN + live translated label. Any asset with non-production status or derivative candidate record is excluded from the release asset registry.

Agents should follow each `nextWork` in this order: `verify_and_consolidate_derivatives` (existing three-file candidates), `create_and_verify_derivatives` (clean-only master), `finish_pending_master_qa`, then `create_clean_type_thumb` (new concept). The five agents continue to own disjoint unique asset IDs, per-asset records and actual image binaries, not a shared manifest. Use exact SHA256/bytes/dimensions/locale rights and matching source revision before promotion.

Lane D may consume `manifest.assets` and `manifest.byContent` generated by the binary audit. It should not use this coverage report to display unverified candidates. The coverage report is for production planning and audit metrics, not app-published content. The two registry keys `emotion:anxiety_worry` and `emotion:anxious` resolve to the same audited asset, provided the canonical mapping has passed validation.

Human review and real-device tests are separate evidence classes. Never mark those as passed using merely file metadata or unit tests.
