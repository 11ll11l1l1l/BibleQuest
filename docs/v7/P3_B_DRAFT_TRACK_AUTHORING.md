# P3-B curriculum authoring boundary

Lane B owns the bounded curriculum-authoring service surface under `src/features/curriculum-authoring/` and focused unit coverage. The implementation uses the integrated `v7_tracks`, `v7_modules`, `v7_lessons`, `v7_lesson_revisions`, and `v7_lesson_steps` tables plus authenticated RLS without schema or policy changes.

`createTrackAuthoringRepository({client,getContext})` provides congregation-scoped track listing, draft creation, and optimistic draft updates. `createHierarchyAuthoringRepository({client,getContext})` extends the same boundary to module and lesson listing plus draft creation/editing. `createLessonRevisionAuthoringRepository({client,getContext})` adds draft lesson-revision creation, revision/step listing, and one-position step upserts for the canonical seven-step flow. Composition supplies the existing authenticated client/provider and a current context callback returning `userId`, `congregationId`, and `canAuthor`. Derive that capability from trusted membership/role state, never form values or user-editable metadata. Client capability checks are UX/recovery guards; database RLS remains authorization. Global/null-congregation authoring stays outside this scoped interface.

Track creation stamps actor, tenant, and draft state internally. Module and lesson creation derive parent identifiers after verifying the hierarchy belongs to the active congregation; mutations require draft parents. Track/module/lesson edits require the caller's loaded revision ID, match the stable ID/parent/draft state/revision atomically, then rotate revision identity. Empty update results mean stale or noneditable conflict. Draft lesson revisions derive `created_by`, canonical locale, and the next revision number after the full draft parent hierarchy is revalidated; concurrent revision-number conflicts are surfaced and never silently retried. Account/congregation changes and capability revocation invalidate pending responses.

Lesson-step authoring derives `step_type` exclusively from position 0–6, mapping to `Scripture → Understand → Discuss → Reflect → Apply → Pray → Action`. Step content and Scripture-reference payloads must be bounded JSON-safe data, and optional Library revision links must be valid identifiers. Each save uses one `lesson_revision_id,position` upsert and then validates the returned step identity/type. Published lesson revisions are rejected before mutation and remain protected by the database immutability trigger.

Published hierarchy is intentionally not changed through these draft methods. Authorized publish/archive behavior remains the unresolved P3-B persistence boundary. It must not be implemented as a chain of client writes that could partially publish a track, module, lesson, revision, or steps. Publication must preserve the immutable published lesson revision and exact seven-step snapshot; any schema/RPC requirement goes through the serialized schema owner. Assignment/start UI preparation and author-route/navigation composition remain shared handoffs; Lane B does not create a new global route key, session owner, tenant store, migration, or RLS policy.

Evidence so far: track authoring has eight focused tests, module/lesson hierarchy authoring adds ten, and lesson-revision/step authoring adds ten. Coverage includes input/authority-field validation, tenant/parent scoping, bounded reads, optimistic revisions, draft-only mutation, stale conflicts, canonical seven-step mapping, JSON payload safety, immutable published revisions, context invalidation, and database-denial propagation. The newest ten tests pass locally via `node --test`, with source syntax checked before push. Repository CI/preview remains the integration check. Query doubles are not live backend/RLS certification. No production writes, V7 DDL, publication, archive, or complete author-journey acceptance is claimed.
