# P3-B curriculum authoring boundary

Lane B owns the bounded curriculum-authoring service surface under `src/features/curriculum-authoring/` and focused unit coverage. The implementation uses the integrated `v7_tracks`, `v7_modules`, and `v7_lessons` tables plus authenticated RLS without schema or policy changes.

`createTrackAuthoringRepository({client,getContext})` provides congregation-scoped track listing, draft creation, and optimistic draft updates. `createHierarchyAuthoringRepository({client,getContext})` extends the same boundary to module and lesson listing plus draft creation/editing. Composition supplies the existing authenticated client/provider and a current context callback returning `userId`, `congregationId`, and `canAuthor`. Derive that capability from trusted membership/role state, never form values or user-editable metadata. Client capability checks are UX/recovery guards; database RLS remains authorization. Global/null-congregation authoring stays outside this scoped interface.

Track creation stamps actor, tenant, and draft state internally. Module and lesson creation derive their parent identifiers from method arguments after verifying that the parent hierarchy belongs to the active congregation; mutations require draft parents. Track/module/lesson edits require the caller's loaded revision ID, match the stable ID/parent/draft state/revision atomically, then rotate revision identity. Empty update results mean stale or noneditable conflict. Account/congregation changes and capability revocation invalidate pending responses. A stale response after a completed write does not undo persistence; reload the original scope before retrying.

Published hierarchy is intentionally not modified through these draft methods. Publishing a curriculum path must not be implemented as a chain of client writes that could partially publish a track, its modules, lessons, revisions, or steps. Seven-step lesson revision preparation plus authorized publish/archive behavior remains the next P3-B persistence boundary and must preserve immutable published lesson revisions and the canonical `Scripture → Understand → Discuss → Reflect → Apply → Pray → Action` order. Route/navigation composition and the authorized author surface remain a shared Lane A handoff; this lane does not create a new route key, session owner, or tenant store.

Evidence so far: the original track boundary has eight focused tests. The module/lesson hierarchy boundary adds ten focused Node tests covering field validation, parent/tenant scoping, bounded lists, draft-only parents, derived parent/state writes, optimistic revision filters, stale conflicts, foreign hierarchy responses, account/congregation invalidation, and database denial propagation. The new hierarchy tests pass locally on Node via `node --test`; repository CI/preview remains the integration check. These query doubles are not live backend/RLS certification. No production writes, V7 DDL, or publication claims are made. Browser and complete author journey acceptance remain open.
