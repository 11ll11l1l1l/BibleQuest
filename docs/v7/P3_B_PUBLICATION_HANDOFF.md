# P3-B publication readiness and shared mutation handoff

Starting integration: `72ae1c13456edfb4914728b1495b60d16ddbcd30`.

Lane B now owns read-only publication readiness in `src/features/curriculum-authoring/publication-readiness.js`. It revalidates the exact congregation-scoped Track → Module → Lesson → lesson-revision path, reads at most seven canonical lesson steps, rejects malformed/foreign responses, and produces a stable publish request only when the full hierarchy is still draft, the selected revision is unpublished, and positions 0–6 are present exactly once with the canonical step types. The request includes the current track/module/lesson revision IDs so the eventual mutation boundary can reject stale authoring state. Optional Library revision references are returned for backend verification; readiness never treats a client read as permission to publish them.

This module performs no publication, withdrawal, archive, assignment, or production write. Authenticated RLS remains authority and `canAuthor` remains only a trusted composition/UX guard. Pending responses are invalidated when account or congregation context changes.

Atomic publication/archive is a serialized schema-owner dependency tracked in GitHub issue #1168. The current tables/triggers can prevent publishing a lesson revision without seven steps and can keep published revision/steps immutable, but separate client updates to the revision, lesson, module, and track could expose a partially published hierarchy. Lane B therefore will not add that chain. The backend boundary must perform all hierarchy/state/staleness/authorization checks and state changes in one transaction and return stable IDs/state for client validation.

Assignment/start preparation is also not allowed to create duplicate assignment authority. The existing discipleship adapter reads `v7_pair_assignments` and deliberately fails when more than one active assignment identifies the same pair/revision. Before Lane B adds an assignment mutation, the shared owner must confirm the single authoritative assignment lifecycle and a race-safe uniqueness/transaction contract; P1-C also records that assignment lifecycle must not be duplicated. A feature-local author/mentor chooser can consume a confirmed mutation later without creating a second session, congregation, or permission owner.

Focused publication-readiness tests cover complete readiness, hierarchy-state blockers, incomplete steps, malformed/duplicate sequences, foreign responses, exact scoped filters/bounds, capability/identifier denial, context switching, and database error propagation. This is static/query-contract evidence only. Live backend/RLS, browser authoring, atomic publication/archive, assignment creation, and end-to-end author journey acceptance remain OPEN.
